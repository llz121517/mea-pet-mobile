# ADR 0002：兜底上下文容量取小窗口（32K），不取大窗口（128K）

- 状态：已采纳（2026-11-19，1.9.0 dev）
- 相关代码：`ContextCapacity`（`FALLBACK_CAPACITY_TOKENS` / `LOOPBACK_FALLBACK_CAPACITY_TOKENS`）、`ContextCapacityProvider`、`ContextCapacityParser`（`client/ContextCapacity.kt`）

## 背景

上下文窗口只能靠探测 `/models` 响应推断，探测不到时必须有兜底值。不同服务商的真实窗口差距很大（32K ~ 128K 以上），兜底值一旦选错，代价并不对称：

- **估大**（按 128K 假设，真实只有 32K）：请求整体超长，被服务端直接以 400 拒绝。用户等待一次完整往返却只拿到失败，且该轮消息需要回滚重发。
- **估小**（按 32K 假设，真实有 128K）：只是提前压缩或截断历史，模型仍能正常回答，未用满的窗口在下一轮继续可用，不影响正确性。

## 决策

兜底原始容量统一取 **32768**（乘 0.85 系数后约 27852）。云端、私网、回环使用同一套逻辑，回环常量保留独立定义但当前同值。

优先级仍为：用户手动填写 > 探测值 > 兜底值。兜底只在探测无结果时生效，用户可在设置页填写实际窗口覆盖。

## 后果

- 最坏情况从「请求被拒、白等一次往返」降级为「提前压缩/截断」，两害相权取其小。
- 探测失败或服务不暴露容量字段时，应用默认工作在保守预算下；需要更大上下文的用户手动填写即可。
- 不接受「按服务商维护内置窗口表」或运行时学习：那会引入按厂商分支与维护负担，违背通用逻辑优先（`docs/rules.md`）。
- 若后续实测显示探测命中率过低、保守预算成为常态体验瓶颈，再考虑引入外部容量目录，届时另起 ADR。
