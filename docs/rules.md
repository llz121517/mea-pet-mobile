# 项目规则

## 通用逻辑优先

实现跨服务商 / 跨模型 / 跨数据格式的适配时，写通用逻辑：

- 不为单个服务单独写 `if`；
- 不设内置表；
- 不设白名单；
- 不做运行时学习。

识别 / 解析失败时直接降级到兜底值，不做特殊补救。

> 来源：[`2026-11-18-sqlite-context-plan.md`](2026-11-18-sqlite-context-plan.md) §0 决策 7；记忆系统当前实现参考见 [`2026-11-18-memory-tools-plan.md`](2026-11-18-memory-tools-plan.md)。

## 童子军规则优先

日常开发优先践行童子军规则：让经手的代码比接手时更整洁一点。处理功能或缺陷时，顺手改善当前范围内已经理解、风险低且容易验证的问题，例如删除无用导入、修正误导注释、改善命名或简化条件。

改善应小而聚焦；跨模块重构、较大改造或不确定的问题先记入 [`TODO.md`](TODO.md)，另行处理。整理改动与功能改动分开提交，便于审查和独立回退。

## 过时文档直接删除

过时且会误导的文档直接删除，不进归档（需要追溯查 git 历史）。

## CHANGELOG 写作规则

`### Fixed` 只记录**修复已发布版本缺陷**的条目。

判断依据：该行为在**上一个发布 tag**（如 `v1.8.0`）里是否存在。

- 存在 → 是真修复，写进 `### Fixed`；
- 不存在（本次开发期新建功能自带的问题）→ **直接修正，不写进 CHANGELOG**。对用户而言那是新版本自带的正确行为，不是「修了旧版本的 bug」，写成 Fixed 会高估本版的修复价值。

同一逻辑适用于 `### Changed` 里描述「此前如何、现在如何」的措辞：只与已发布版本对比，不把开发过程中的中间态当成「此前」。

**只作用于尚未发布的版本段。** 已发布版本的历史条目保持原样：那些记录对从更早版本升级上来的用户仍有说明价值，事后改写会与用户实际看到的发布说明不符。1.8.0 发布前曾做过一次同样的整理（`8c7738f`：开发期引入的问题从 Fixed 并入 Changed），可作为先例参考。

## 提交规范

### 提交格式

提交信息标题使用 Conventional Commits 格式 `type(scope): 描述`（scope 可选）；type 不限于规范列表，可以使用 `change` 这类自定义值。长说明写进 commit message。

### 提交内容

- 多笔小改动合并成一笔提交。
- 独立功能或较大改动应按职责拆为多笔提交，不因在同一轮完成就合并。

### 提交与 Push 时机

- 一个改动完成后（未完成时不要提交）默认提交。
- 多次修改同一地方时，应使用 amend 提交。
- 仅要求 Push 时 Push。
