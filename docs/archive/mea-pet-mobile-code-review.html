#1 lifeMap 多协程无锁并发修改非线程安全 Map
并发 并发隐患（已降级）
文件: viewmodel/ChatViewModel.kt :82-113, 392-405 （原报告误标 335-340）

lifeMap 是一个普通 LinkedHashMap，同时被 collect 协程读写，又被每个 scheduleRemove 启动的独立协程 remove。两个或多个协程无任何同步机制并发修改同一非线程安全 Map，极易抛出 ConcurrentModificationException 或丢失更新。

// collect 协程中写
lifeMap[newMsg.id] = Triple(SystemBubblePolicy.BASE_LIFE_MS, job, 0)
sysIds.forEachIndexed { index, id ->
    lifeMap[id] = Triple(newLife, newJob, newCount)  // ← 写
}

// scheduleRemove 启动的独立协程中删
private fun scheduleRemove(
    lifeMap: MutableMap<String, Triple<Long, Job, Int>>,
    msgId: String, delayMs: Long
): Job = viewModelScope.launch {
    kotlinx.coroutines.delay(delayMs.milliseconds)
    removeBubble(msgId)
    lifeMap.remove(msgId)  // ← 另一协程并发删
}
系统气泡数量增多时，倒计时协程与 collect 协程同时操作 lifeMap，可能崩溃或气泡错乱。
复查修订（2026-08-31）：部分属实，「可能崩溃」结论不成立，P0 降级为 P2 加固

事实层面属实：lifeMap 确为无同步的 LinkedHashMap（ChatViewModel.kt:82），collect 协程写（:90/:110）、scheduleRemove 协程删（:399/:404）。但 ConcurrentModificationException 实际不可能发生：

① 所有访问均经 viewModelScope.launch，运行在 Dispatchers.Main.immediate 单线程调度器上，不存在并行执行；② 代码从未对 lifeMap 本身做迭代（sysIds.forEachIndexed 迭代的是 List，map 只有按 key 的 get/put/remove），且 collect lambda 内各 map 操作之间无挂起点。线程封闭消除了竞争。保留为加固项：结构依赖「恰好都在主线程」的隐式前提，建议注明线程约束或 actor 化。

建议修复

改用 Mutex 保护所有 lifeMap 访问，或更好：将气泡生命周期管理收敛到单一 actor 协程（Channel 接收消息），避免跨协程共享可变状态。

#2 ApiResponse.modelIds 吞掉 CancellationException，破坏协程取消语义
并发 协程泄漏
文件: client/model/ApiResponse.kt :43-56

catch (_: Exception) 会捕获 kotlinx.coroutines.CancellationException。该函数被 SettingsViewModel.fetchModels 在 withContext(Dispatchers.IO) 中调用，若用户离开页面导致协程取消，取消信号被吞掉，协程不会正确终止。

fun modelIds(body: String): List<String> = try {
    // ...解析逻辑...
} catch (_: Exception) {  // ← 吞掉 CancellationException
    emptyList()
}

同文件的 chatCompletionContent 已用 runCatchingLog（正确重抛 CancellationException），唯独此处裸 try-catch，风格也不一致。

复查修订（2026-08-31）：属实，但实际危害极低

modelIds 是纯同步 JSON 解析（ApiResponse.kt:43-56）、无任何挂起点，实践中 CancellationException 几乎不可能在此抛出，「协程泄漏」场景难以真实发生。修复仍值得做（成本一行），动机是统一项目错误处理约定（ErrorHandling.kt:11-14 明确要求重抛 CE）而非防崩溃。优先级可从 P0 适当放宽。

建议修复
catch (e: CancellationException) { throw e }
catch (e: Exception) { Log.w(TAG, ...); emptyList() }
#3 ConversationManager.trimWindow 破坏消息原始顺序
逻辑 数据错乱
文件: chat/ConversationManager.kt :188-200

裁剪窗口时 messages.addAll(systemMessages + trimmed) 把所有 system 消息整体提到列表最前，彻底打乱 system 与 user/assistant 的原始交错顺序。

private fun trimWindow() {
    if (messages.size <= maxSize) return
    val systemMessages = messages.filter { it.role == ChatRole.system }
    val nonSystem = messages.filter { it.role != ChatRole.system }
    // ...
    messages.clear()
    messages.addAll(systemMessages + trimmed)  // ← system 全部挪到最前
}
复查修订（2026-08-31）：属实，但实际影响有限

乱序属实（ConversationManager.kt:190-197）。但 buildApiMessages（:113-114）发请求时会过滤 history 中的 system 消息并自行重组 system 前缀，因此对发给模型的内容影响有限，主要影响内存中 history 的排列（以及将来若改用原序消费 history 时的隐患）。仍建议按原方案修复。

建议修复

采用就地逐条裁剪（removeAt(0)）保留原序，或按原始 index 排序后保留尾部 maxSize-trimBatch 条。

#5 MarkdownText 缓存键与构造参数不一致，返回陈旧实例
缓存 渲染错乱
文件: ui/component/MarkdownText.kt :86-111

markwonCache 缓存键仅 dark: Boolean，但 textSizePx 与 tableBorder 参与构造。首次以某 dark 值调用决定缓存实例后，同 dark 不同参数命中旧实例，返回陈旧的 Markwon。设备密度变化或多密度场景下公式字号、表格边框色错乱。

private val markwonCache = ConcurrentHashMap<Boolean, Markwon>()

private fun obtainMarkwon(
    context: Context, dark: Boolean, textSizePx: Float, tableBorder: Int
): Markwon = markwonCache.getOrPut(dark) {  // ← 键只有 dark
    Markwon.builder(context)
        // ... .usePlugin(TablePlugin.create(...tableBorder...))
        // ... .usePlugin(JLatexMathPlugin.create(textSizePx) ...)
        .build()
}
复查修订（2026-08-31）：属实，但影响面收窄

tableBorder 实为 dark 的纯函数（MarkdownText.kt:146 if (dark) ... else ...），同 dark 下不可能不同，不会造成陈旧命中；真正会发散的只有 textSizePx（:145，来自 LocalDensity，系统字体缩放/显示密度变化时同 dark 会命中旧实例）。场景存在但触发条件苛刻，修复建议不变（缓存键纳入全部构造参数）。

建议修复

将 textSizePx 和 tableBorder 纳入缓存键（如 data class MarkwonKey(dark, textSizePx, tableBorder)），或证明它们在生命周期内不变并加 assert。

#6 OverlayMenu 条件分支内调用 collectAsState，违反 Compose 规则
Compose 复查：不属实，已撤回
文件: ui/component/OverlayMenu.kt :75-78

collectAsState 是 Composable 函数，却被放在 if (container != null) 条件分支里。Compose 要求 Composable 调用不能依赖运行时条件分支，否则编译器生成的 groups 不稳定，可能导致状态丢失或运行时异常。

val mainVoiceOn = if (container != null) {
    container.settingsManager.ttsMainEnabledFlow.collectAsState(initial = false).value
} else false
复查修订（2026-08-31）：不属实，本条撤回

「违反 Compose 组合规则」的定性错误：Compose 明确允许可组合函数的条件调用，编译器通过 group 插入/移除正确处理分支切换，不会崩溃或行为异常。container 经 remember(context)（:74）稳定化，分支变化只会触发正常的订阅/退订。最多算风格可议（可早退或对空 flow 取 collect），并非缺陷，无需修复。

建议修复（已作废，仅供参考）

在分支前无条件 collectAsState，或将 container == null 提为外层 if (container == null) return 早退。

#7 ConversationStore.persistAsync 作用域取消后静默丢数据
持久化 数据丢失
文件: chat/ConversationStore.kt :init block + persistAsync

传入的 scope 一旦取消，collector 协程结束，之后所有 persistAsync 只往 MutableSharedFlow（replay=1, DROP_OLDEST）里 emit，没有任何报错，数据静默丢失。

#10 跨模块通信用 companion object var 回调（全局可变状态）

#11 消息源不一致，ViewModel 需复杂 merge 补丁
数据一致性 脆弱
文件: viewmodel/ChatViewModel.kt (mergeWithHistory)

ConversationManager 有滑动窗口裁剪，而 ViewModel.messages 从不裁剪——两份真相源不一致。mergeWithHistory 用 takeLast(5) 魔法数字补丁弥合差异，逻辑复杂且脆弱。

复查修订（2026-08-31）：核心论点属实，机制描述有偏差

takeLast(5)（ChatViewModel.kt:185）只是分界 id 在 current 中找不到时的保守兜底分支；主弥合机制是「以 history 最后一条 id 为分界，之前以 history 为准、之后保留尾部」（:176-189，KDoc :146-152 有明确说明）。双消息源、一边裁剪一边不裁剪的核心问题成立。

建议

让 ConversationManager 成为唯一消息源，ViewModel 直接订阅其 Flow，不再自维护副本。

#38 LogExporter Process.waitFor() 无超时，可能永久阻塞 IO 协程

#39 MarkdownText.update 每次 recomposition 都 setMarkdown 重新解析

#44 ChineseG2p.ensureDict check-then-act 竞态
